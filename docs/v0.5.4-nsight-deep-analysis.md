# v0.5.4 RTX 3080 Nsight deep profile

Validation platform:

- GPU: NVIDIA GeForce RTX 3080 10 GB, compute capability 8.6
- HiveOS: current R1 installation used for the v0.5.4 live run
- NVIDIA driver: 610.43.03
- CUDA compiler: 12.4
- profiled profile: `lookup-finite-mono64`
- launch: 1,024 blocks x 64 threads
- profile size: 262,144 nonces

The kernel is decisively compute-bound. Matrix and lookup traffic have substantial cache headroom, while the FP64 pipeline is the dominant utilized execution resource.

## Primary bottlenecks

### 1. Rare nonlinear path causes severe SIMT under-utilization

Only 8.38 of 32 lanes are active on average. The HooHash state variable `sw` selects a mostly cheap scaled-nibble lookup path and a rare transcendental path. Different nonces enter the nonlinear path at different iterations, so warps repeatedly execute sparse `sin`, `cos`, `exp`, division and square-root work.

Nsight estimates 60.7% potential improvement from eliminating inactive/predicated lanes. This is an upper bound rather than a realizable claim, but it identifies control-flow divergence as a first-order problem.

### 2. Short-scoreboard latency dominates issue spacing

The kernel spends 28.15 of 36.86 cycles between issued instructions waiting on short-scoreboard dependencies. Nsight attributes this class to MIO/special-math/dynamic control dependencies. Memory bandwidth is too low for global-memory traffic to explain the result; the evidence is consistent with the consensus-required FP64 transcendental chain.

### 3. Register allocation limits occupancy

The entry kernel uses 87 registers/thread. Registers cap theoretical occupancy at 41.67%, with 34.93% achieved. The previous build passed `--maxrregcount=80`, but ptxas reported that the global cap was overridden by the entry-specific value derived from `__launch_bounds__`. Therefore prior “register cap” profiles did not actually test the requested cap on the production kernel.

### 4. FMA recommendation is not directly usable

Nsight reports 132,677,052 fused and 93,382,486 non-fused FP64 instructions and estimates up to 20.65% local improvement from additional fusion. HooHash V110 is rounding-order sensitive, and the project intentionally compiles CUDA with `--fmad=false`. Enabling contraction without a consensus proof would change hashes, so v0.5.6 does not use this unsafe shortcut.

## v0.5.6 experiment

v0.5.6 retains the validated v0.5.4 monolithic lookup/finite implementation and tests only consensus-gated transformations:

1. reorder `accumulate()` so the common scaled-lookup path is laid out first;
2. outline rare transcendental leaves (`sincos+exp`, `sin²`, reciprocal square root);
3. outline the full nonlinear selector or the complete safe nonlinear path;
4. optionally remove `__launch_bounds__` so `--maxrregcount` becomes effective;
5. test real 80, 72 and 64-register caps plus 64/96/128-thread geometries;
6. reject every profile that fails native tests, 16,384 CPU/CUDA samples or consensus vectors;
7. emit `TARGET_2MH=PASS` only when the internal benchmark reaches at least 2,000,000 H/s.

No performance claim is made until the RTX 3080 autotuner and a live-pool run validate the selected profile.
